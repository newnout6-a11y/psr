# План: Регистрация аккаунтов Kwork (только email + ссылка подтверждения)

## Контекст

В проекте PSR на данный момент нет поддержки создания новых аккаунтов Kwork. Вся авторизация опирается на уже существующие сессии:
- Основной способ: куки из Session Hub (`scripts/session_hub/*`)
- Запасной: `KWORK_EMAIL` / `KWORK_PASSWORD`, передаваемые в клиент библиотеки `kwork` (`src/platforms/kwork.py`)

Подробный reverse-инжиниринг фронтенда (файл `docs/kwork_registration_api_analysis_20260713.md`, дата 2026-07-13) полностью восстановил клиентский контракт email-регистрации:
- Эндпоинты: `GET /api/ban/disallowfreeregister`, `GET /api/user/checkemail`, `POST /api/user/checklogin`, `POST /api/user/signup` (или `simplesignup`)
- Тело запроса — `multipart/form-data`
- Генерация логина на клиенте + валидация
- Основная CAPTCHA — Yandex SmartCaptcha, запасная — Google reCAPTCHA
- Телефон для email-пути не требуется

Пользователь после ручной проверки подтвердил:
- Ветка с телефоном не нужна.
- Достаточно только почты + пароля + "ссылки" (verification link).
- Файл «Текстовый документ (4).txt» на рабочем столе описывает провайдера firstmail.ltd (REST + IMAP), который используется для получения временных почт и чтения писем с ссылками подтверждения от Kwork после регистрации.
- «Почта и пароль» — это учётные данные firstmail (используются и как email для регистрации на Kwork, и для опроса ящика).
- «Ссылка» — это ссылка подтверждения/активации аккаунта, которую нужно получить через API firstmail и перейти по ней.

Цель: реализовать надёжное автоматическое создание аккаунтов Kwork (покупатель или продавец), которые потом можно использовать через существующие механизмы авторизации (логин/пароль или куки).

Это позволит заниматься фармингом аккаунтов, тестированием, работой с несколькими аккаунтами и т.д., при этом максимально переиспользуя существующие прокси, pacing, логирование и HTTP-паттерны проекта.

## Рекомендуемый подход

Реализовать **прямые веб-запросы к API** (точно по восстановленному контракту), а не браузерную автоматизацию и не расширение библиотеки `kwork` (библиотека предназначена для уже авторизованных запросов к мобильному/веб API).

1. Добавить поддержку регистрации внутрь `KworkService` (или отдельного helper'а), чтобы это было наравне с `get_api()`, веб-инбоксом и т.д.
2. В точности повторить предрегистрационную последовательность из анализа:
   - GET /api/ban/disallowfreeregister
   - GET /api/user/checkemail (обработать "уже существует" / стоп-лист)
   - Сгенерировать кандидата username из локальной части email (транслит RU→EN, очистка до [a-z0-9_-], 4–20 символов, запрет kwork/support)
   - POST /api/user/checklogin (с getFreeLogin, опционально forceGenerate) до успеха
3. Сформировать и отправить точный FormData на `POST /api/user/signup` (сначала обычный режим, при необходимости fallback на simplesignup).
   - tz в стиле Intl или "Europe/Moscow"
   - userType (по умолчанию 1 = покупатель, 2 = продавец)
   - Обработка поля `recaptcha_show` в ответе (в первой версии — graceful fail или поддержка тестового пути без капчи; позже можно добавить браузер или солвер)
4. При успешном ответе регистрации извлечь csrftoken / redirect / token.
5. Опросить ящик firstmail (по переданным email + password или Bearer-key) и найти письмо от Kwork с активационной "ссылкой".
6. Перейти по ссылке активации (тот же клиент httpx с прокси/UA, follow redirects). Подтвердить успех.
7. Опционально сразу попробовать авторизовать созданный аккаунт через существующий клиент Kwork или вернуть структурированный результат (email, kwork_password, cookies при наличии, статус).
8. Экспонировать через FastAPI-роут, чтобы desktop, orchestrator и скрипты могли вызывать.
9. Добавить небольшой клиент firstmail (новый файл в utils), потому что чтения почты в проекте пока нет.
10. Максимально переиспользовать существующую инфраструктуру:
    - Ротация прокси + VPNTE (`vpnte_proxy` + `kwork_ext.ProxyRotator`)
    - Заголовки / User-Agent, которые уже используются для запросов к kwork.ru
    - Логирование (loguru)
    - Rate pacing (`RatePacer` из kwork_ext) — применять умеренно
    - Стиль обработки ошибок
11. Делать только email-путь (без телефона). Поддерживать опциональное поле `user_promo` / реферальную ссылку, если "ссылка" в некоторых случаях окажется промо.
12. Сохранять результаты (метаданные созданных аккаунтов) в RUNTIME_DIR для последующего использования через Session Hub или manual cookies.

**Почему не альтернативы:**
- Полная браузерная автоматизация (camoufox / nodriver) тяжелее, медленнее и избыточна для простого API-флоу, который уже полностью описан в анализе.
- Расширение pip-пакета `kwork` не нужно (регистрация — это веб-эндпоинты, а не мобильный контракт библиотеки).
- Просто возвращать ссылку без авто-активации — менее завершённое решение; пользователю нужны рабочие аккаунты.

Примечание по CAPTCHA: если на практике Yandex SmartCaptcha всегда требуется, позже можно расширить план шагом через браузер (в `browser/` уже есть camoufox_manager). В первой реализации пробуем прямой путь и явно возвращаем `recaptcha_show`.

## Спецификация клиента firstmail (из «Текстовый документ (4).txt» на рабочем столе)

Базовый URL: `https://api.firstmail.ltd/v1/`

Основные эндпоинты для получения ссылки подтверждения:
- `GET /v1/mail/one` — последнее одно письмо
- `GET /v1/get/messages` — список (максимум 1000), мощные фильтры: from / _from / _from_not, subject, body, query, before/after, folder, read/unseen, uid, action (DELETE / TRASH / UNSEEN)
- `GET /v1/download/attachment` — скачивание вложения

Авторизация:
- Заголовок `Authorization: Bearer <ключ>`
- Плюс параметры email + password (или login/pass) в запросах чтения почты
- Пример ключа есть в документе (НЕ хардкодить! брать из env `FIRSTMAIL_API_KEY` или передавать при вызове)
- Альтернатива: полноценный IMAP (`imap.firstmail.ltd:993`, SSL) + библиотека nichind/firstmail при необходимости REST.

Письмо с подтверждением от Kwork ожидается от адреса вида noreply@kwork.ru и содержит явную ссылку активации в теле.

Реализация клиента firstmail должна быть минимальной, по возможности асинхронной, использовать httpx и работать под теми же прокси.
