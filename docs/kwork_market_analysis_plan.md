# План анализа рынка Kwork и выбора собственных услуг

Дата фиксации: 2026-07-12
Статус: согласованная архитектура и продуктовый план. Локальный семантический анализ и enrichment-пайплайн еще не реализованы полностью.

## 1. Цель продукта

PSR нужен не для показа общей статистики Kwork, а для конкретного решения:

> какие услуги выставить человеку с нулем отзывов, чтобы не быть очередной копией уже существующих предложений.

Порядок развития:

1. Сначала анализ предложений и конкурентов.
2. Затем генерация собственных карточек и публикация.
3. После этого - связка с поиском покупателей.

Приоритет - автоматизация процесса, а не ручной просмотр тысяч карточек.

## 2. Главный принцип обработки

Большая часть работы выполняется локально:

- сбор и хранение данных;
- обогащение карточек отзывами и профилями;
- очистка и дедупликация;
- семантическое объединение похожих услуг;
- подсчет спроса, активности и конкуренции;
- поиск аномалий и ложных возможностей;
- отбор групп для финального решения.

Terra подключается только после локального отбора. Она не должна читать все 6 000-10 000 сырых карточек.

## 3. Жесткое правило цены

Карточка с ценой строго больше `15 000 ₽` сразу исключается из рабочего набора:

```text
price > 15000 -> reject_price
```

Она может остаться в raw-БД для истории, но не получает embeddings, enrichment, кластеризацию и не попадает в Terra.

Премиальный сегмент отдельной группой не выделяется.

## 4. Подтвержденный сбор данных

### 4.1. Полный веб-сбор

Основной endpoint:

```text
POST https://kwork.ru/catalog_kworks_filters/{canonical_alias}
```

Параметры первого запроса: `page`, `pageSize` и фильтры. Продолжение выполняется через:

```text
excludeIds=<comma-separated-listing-ids>
onePage=1
```

Известная структура ответа:

```text
success
  -> data
    -> stateData
      -> viewData
        -> filters
        -> kworks
          -> posts
            -> data[]
```

В текущем реальном job по категории «Разработка и IT» сохранено `6384` уникальных карточки. Сервер сообщал `total_found=100736`; этот запуск был остановлен раньше полного покрытия категории.

### 4.2. Поля карточки

В raw-карточках подтверждены:

- `id`;
- `gtitle` - название;
- `price`;
- `days`;
- `queueCount`;
- `userName` и `userId`;
- `userRating`;
- `userRatingCount`;
- `sellerLevel`;
- `sellerIsNotAvailable`;
- `userIsOnline`;
- `url`;
- `photo`, `photoSrcset`, `picture`;
- `portfolios`, `portfolioPictures`, `portfolioVideos`;
- данные объема услуги и служебные флаги.

В карточке нет полноценного описания, инструкций, даты регистрации продавца и истории отзывов.

### 4.3. Быстрый API-срез

```text
POST https://api.kwork.ru/kworks
```

Параметры: `categoryId`, `classifierId`, `page`. Это быстрый срез и источник метаданных, а не основной способ полного прохода рынка.

## 5. Enrichment: недостающие факты

### Карточка

```text
POST /getKworkDetails
```

Дает описание, инструкции, цену, срок, очередь и дополнительные данные конкретного Kwork.

```text
POST /getKworkDetailsExtra
```

Дает:

- `reviews_count` именно этой карточки;
- `goodReviews`, `badReviews`;
- `kwork_ratings`;
- `last_reviews[]`;
- у отзывов есть `time_added`, `good`, `bad`, `text`, `writer`, `answer`.

Для популярности Kwork важнее именно эти отзывы, а не общее число отзывов продавца.

### Продавец

```text
POST /userByUsername
```

Дает:

- `rating`;
- `rating_count`;
- `reviews_count`;
- `addtime` - timestamp, используемый для оценки возраста аккаунта;
- `completed_orders_count`;
- `level_description`;
- `kworks_count`;
- портфолио и другие профильные данные.

```text
POST /userReviews
```

Дает отзывы продавца с `time_added`, текстом, признаком `good/bad`, Kwork и ответом продавца. Для анализа конкретной карточки приоритетнее `getKworkDetailsExtra`.

### Важное различие рейтингов

`userRating` в карточке - нормализованная шкала. В проверенных ответах `100` соответствовало профилю `rating=5.0`, а `98` - примерно `4.9`.

`userRatingCount` обычно соответствует `rating_count`, но не всегда равен настоящему `reviews_count`. Поэтому сохраняются отдельно:

```text
listing_reviews_count  = getKworkDetailsExtra.reviews_count
seller_rating          = userByUsername.rating
seller_rating_count    = userByUsername.rating_count
seller_reviews_count   = userByUsername.reviews_count
```

## 6. Локальная модель данных

Для каждого listing нужно иметь нормализованную запись:

- идентификатор, URL, название;
- цена, срок, очередь;
- seller ID и nickname;
- рейтинг продавца и количество его рейтингов;
- количество отзывов конкретного Kwork;
- последние три отзыва и их timestamps;
- дата проверки и источник данных;
- качество/полнота данных;
- семантическая группа и локальные оценки.

Для продавца отдельно хранятся:

- рейтинг;
- количество рейтингов;
- общее количество отзывов;
- стаж;
- выполненные заказы;
- количество активных Kwork’ов.

Обогащение кэшируется. Профиль продавца запрашивается один раз на уникального продавца, а не для каждой его карточки.

## 7. Как уйти от regex

Regex не используется для определения того, являются ли две карточки одной услугой.

Локальный семантический слой:

1. Нормализует Unicode, регистр, типовой рекламный шум и дубликаты.
2. Сохраняет важные сущности: Telegram, WordPress, API, GPT, платформы и версии.
3. Строит embeddings для названия и, когда нужно, описания.
4. Объединяет карточки по cosine similarity/кластеризации.
5. Разбивает слишком широкие группы на мелкие сервисные подгруппы.
6. Строит название группы по характерным словам, но не принимает решение только по этому названию.

Таким образом, разные формулировки одной услуги могут попасть в одну группу без заранее заданного словаря. Regex остается только для технического извлечения чисел, цены, сроков, версий и ссылок.

Группировка должна быть предметной, а не по широкой нише. Например, разные варианты Telegram-ботов должны разделяться по реальному назначению, а не сливаться в одну группу «боты».

## 8. Локальные показатели

### Активность и спрос

- количество отзывов конкретного Kwork;
- возраст последнего отзыва;
- промежуток между последними тремя отзывами;
- приблизительная частота отзывов;
- очередь заказов;
- доля положительных/отрицательных и автоматических отзывов.

Последние три отзыва - основной сигнал свежести. Если отзывов меньше трех, это низкая доказательность, а не автоматический нулевой спрос.

### Переполненность

- количество семантически эквивалентных карточек;
- количество уникальных продавцов;
- плотность карточек в ценовом диапазоне;
- доля почти одинаковых предложений;
- концентрация активности у лидеров.

### Сила продавца

Рейтинг, число отзывов и стаж продавца не являются причиной сразу выкидывать карточку. Это отдельная характеристика конкурентного барьера.

Высокие отзывы могут означать одновременно:

- сильного конкурента;
- доказанный спрос на услугу.

Поэтому нужно разделять `demand_proof` и `entry_barrier`.

### Цена и аномалии

Сравнение цены выполняется внутри узкой семантической группы. Используются медиана и квантили, а не простое среднее.

Карточка с необычно высокой ценой до `15 000 ₽` не считается автоматически плохой: она получает флаг `price_outlier` и проверяется вместе с отзывами, описанием и активностью. Карточки выше `15 000 ₽` отбрасываются без исключений.

## 9. Три итоговых состояния

После локальной обработки каждая рабочая группа получает одно из трех состояний.

### 1. Популярная и переполненная

- много семантически одинаковых карточек;
- свежие отзывы есть;
- активность регулярная;
- основную долю активности забирают сильные продавцы.

Спрос доказан, но вход сложный.

### 2. Перспективная для входа

Объединяет небольшие группы с реальным спросом и популярные, но доступные группы:

- есть свежие отзывы;
- активность получают не только лидеры;
- конкурентов мало или умеренно;
- есть продавцы с небольшим числом отзывов;
- можно сделать отличающееся предложение.

Это главный источник кандидатов для собственной карточки.

### 3. Не брать

Сюда попадают:

- переполненные, но мертвые группы;
- редкие карточки без доказательств спроса;
- семантический шум;
- аномальные предложения без активности;
- карточки с недостаточными данными.

Карточки дороже `15 000 ₽` до этой классификации не доходят.

## 10. Финальный этап Terra

Terra получает не весь рынок, а подготовленные группы по `10-100` представителям. Если группа больше, передается стратифицированная выборка:

- лидеры;
- средний слой;
- новые продавцы;
- ценовые выбросы;
- семантические выбросы.

В dossier передаются агрегаты, последние отзывы, описания финалистов, цены, URLs и ID доказательств.

Terra должна решить:

- настоящая ли это услуга или шум;
- доказан ли спрос;
- насколько рынок переполнен;
- есть ли путь входа продавцу без отзывов;
- чем отличить новую карточку;
- какие пакеты, цену и позиционирование выбрать;
- какие карточки и выводы отвергнуть.

Ответ должен быть строгим JSON с `verdict`, `confidence`, `reasons`, `evidence_ids`, `recommended_offer` и `rejected_cases`. Модель не должна придумывать факты, которых нет в evidence.

Terra получает в первую очередь состояние `Перспективная для входа`, затем наиболее показательные группы `Популярная и переполненная`. Из `Не брать` передаются только пограничные случаи для проверки.

## 11. Подтверждение идеи, поля и генерация

Результат Terra - это рекомендация, а не автоматически опубликованный Kwork. Между анализом рынка и генератором должны быть два отдельных подтверждения.

### 11.1. Рекомендация

После решения Terra формирует спецификацию собственной услуги:

1. Что именно выставить.
2. Для какого сегмента.
3. Какое отличие использовать.
4. Какой диапазон цены выбрать, не превышая `15 000 ₽`.
5. Что включить в пакеты.
6. Какие обещания не использовать.
7. На каких исходных карточках основано решение.

В интерфейсе это состояние `proposed`. Я подтверждаю или отклоняю идею. До подтверждения генератор и публикация не вызываются.

### 11.2. Выбор полей Kwork

После подтверждения идеи открывается отдельный шаг `field_mapping`. Это не часть свободного текста карточки: поля Kwork являются структурированным контрактом формы.

Сначала загружается актуальный манифест для пары `category_id + classifier_id`. Для каждого поля сохраняются отдельно:

- транспортное имя (ключ поля), например `attribute[208]` или `attribute[3610][]`;
- `group_id`;
- отображаемый вопрос/заголовок;
- тип (`radio`, `checkbox`, `select`, `text`);
- признак `multiple` и `required`;
- допустимые варианты с точными `option_id` (числа справа в UI, например `5016` или `726`), label и disabled-состоянием;
- зависимость от родительского варианта, если Kwork подгружает дочерние поля динамически.

Пользователь видит понятные labels, но в запрос передаются только исходные имена и ID Kwork. Terra или локальная эвристика могут предложить значения, однако не могут создавать новые ID или подменять label вместо ID. Перед сохранением выбора backend обязан:

1. удалить неизвестные поля и варианты;
2. привести одиночные поля к одному ID, а множественные - к массиву ID;
3. убрать disabled-варианты;
4. проверить обязательные поля;
5. при смене родителя удалить устаревшие дочерние значения и повторно загрузить манифест.

Только после явного подтверждения полей состояние меняется на `fields_confirmed`, и становится доступной кнопка `Сгенерировать карточку`.

### 11.3. Почему текущий парсер дает неверное состояние

Сейчас манифест собирается из нескольких HTML-фрагментов, а `selection` затем поверхностно объединяется с `manifest.selected`. Из-за этого при смене родительского пункта в состоянии могут остаться значения старого дочернего фрагмента. Подпись поля также извлекается эвристически из HTML и не является надежным ключом: транспортный ключ и человекочитаемый label нельзя смешивать.

Исправление должно быть серверным и детерминированным: нормализованный манифест становится источником истины, а UI только отображает его и отправляет выбранные ID. Для каждого снимка манифеста сохраняются `manifest_hash` и `selection_hash`; при генерации и перед публикацией выбор валидируется заново.

### 11.4. Генерация и публикация

После `fields_confirmed` подтвержденная спецификация вместе с `attribute_manifest` и нормализованным `attribute_selection` передается существующему генератору карточки и обложки. Генератор создает черновик, но не публикует его автоматически.

Пользователь проверяет и редактирует заголовок, описание, цену, срок, FAQ, обложку и поля. Затем остаются существующие защитные шаги публикации: preflight, свежий draft hash, signed token и отдельная фраза подтверждения живой публикации.

Итоговый контракт handoff должен храниться на сервере, а не в URL/localStorage:

```json
{
  "recommendation_id": "rec_...",
  "status": "fields_confirmed",
  "category_id": 41,
  "classifier_id": 3587,
  "service_summary": "Telegram-бот для заявок",
  "price": 4900,
  "work_time": 5,
  "attribute_manifest_hash": "sha256:...",
  "attribute_selection": {
    "attribute[208]": 3587,
    "attribute[3610][]": [3612, 5273361]
  },
  "evidence_ids": ["listing_...", "review_..."],
  "generator_request": "ready"
}
```

Здесь ключи `attribute[...]` - имена контролов, а `3587`, `3612` и `5273361` - ID выбранных вариантов. Их labels берутся из сохраненного манифеста; текст labels в payload публикации не подставляется.

После публикации нужно сохранять связь `published_listing -> source_cluster`, чтобы позже сравнивать просмотры, заказы и отзывы с исходным прогнозом.

## 12. Скорость

Проверенная короткая выборка: `80` read-only запросов при `concurrency=10` завершилась за `4.74` секунды, без ошибок, примерно `16.9 req/s`. На длинном проходе нужно учитывать rate limit и backoff.

Для текущих `6384` карточек:

- после ценового фильтра остается `6052`;
- уникальных продавцов остается `2261`;
- полный enrichment всех listing extras: ориентировочно `8-15 минут`;
- embeddings и кластеризация: обычно меньше `1-2 минут`;
- профили продавцов-кандидатов: `1-3 минуты`;
- Terra пакетно: `1-4 минуты`.

Сбор и enrichment запускаются конвейером одновременно. Целевое время первого полного прохода - примерно `12-22 минуты`, при ограничениях Kwork возможен диапазон до `30 минут`.

Для `10 000` карточек целевой диапазон - примерно `18-30 минут`, а не час.

Ускорители:

- фильтр цены до любых дорогих запросов;
- enrichment сразу после появления карточки;
- кэш профилей продавцов;
- кэш `getKworkDetailsExtra`;
- embeddings по хешу текста;
- описания только для неоднозначных и финальных групп;
- возобновление с сохраненного cursor;
- Terra только для отобранных групп.

## 13. Текущая AI-конфигурация

Используется OpenAI-compatible провайдер без хранения ключа в этом документе:

```text
base_url: https://byesu.com/v1
wire_api: responses
final_model: gpt-5.6-terra
final_reasoning: high
```

Для старого map/reduce-пайплайна настроены:

```text
map_model: gpt-5.6-luna
map_reasoning: high
reduce_model: gpt-5.6-terra
reduce_reasoning: high
```

Responses tool loop воспроизводит локальные function-call outputs, потому что провайдер фактически возвращает `store:false`. История Market Assistant хранится локально.

Текущий map/reduce уже умеет большие чанки примерно `506-523 тыс. символов`, но это временный fallback. Для полного рынка предпочтителен локальный semantic/scoring pipeline, чтобы Terra не разбирала десятки сырых чанков.

## 14. Технические пробелы перед реализацией плана

- Сохранение `last_reviews[]` и их timestamps в durable enrichment-таблице.
- Сохранение `addtime` и точного seller profile snapshot.
- Разделение seller-level и listing-level review metrics в схеме и API.
- Локальная модель embeddings и устойчивые пороги fine-grained кластеров.
- Локальный расчет трех состояний и объяснений/evidence.
- Enrichment cache с TTL и возобновлением.
- Перевод Market Assistant с snapshot-ограничения `250` карточек на DB-backed чтение полного job.
- Формальный JSON-контракт dossier для Terra.
- Нормализация `attribute_selection` по манифесту: запрет неизвестных/disabled ID и проверка cardinality.
- Инвалидация дочерних полей при смене родительского значения и стабильный `manifest_hash`.
- Разделение этапов `recommendation_confirmed`, `fields_confirmed` и `draft_generated` в durable handoff.

## 15. Порядок реализации

1. Зафиксировать схему `listing_features`, `seller_features`, `listing_reviews`, `semantic_clusters`.
2. Подключить durable enrichment для карточек до `15 000 ₽`.
3. Добавить кэш и возобновление detail/profile запросов.
4. Реализовать локальные embeddings, дедупликацию и fine-grained clustering.
5. Реализовать показатели активности, переполненности, входного барьера и качества.
6. Реализовать классификацию в три состояния.
