# Requirements Document

## Introduction

Комплексная переработка PSR — Python-агента автоматизации поиска и обработки заказов на фриланс-биржах. Проект сфокусирован на единственной рабочей платформе (Kwork), исправлении критического бага парсинга/поиска, повышении качества генерируемых откликов, создании удобного Desktop UI для одного фрилансера, стабилизации пайплайна и удалении мёртвого кода (OSINT, неиспользуемые платформы).

## Glossary

- **Pipeline**: Последовательность этапов обработки заказа: парсинг → фильтрация → скоринг → веттинг → генерация отклика → отправка
- **Kwork_Parser**: Модуль парсинга заказов с платформы Kwork через мобильный API (библиотека `kwork`) с fallback на браузерный парсер
- **Kwork_API_Client**: Обёртка над библиотекой `kwork` (kesha1225/kwork), обеспечивающая авторизацию и вызовы мобильного API Kwork
- **Search_Strategy**: Модуль AI-генерации поисковых запросов на основе профиля разработчика и истории сигналов
- **Orchestrator**: Центральный модуль, управляющий полным циклом обработки заказов
- **Proposal_Generator**: Модуль генерации текста отклика через LLM (Groq)
- **LLM_Router**: Маршрутизатор LLM-провайдеров с health-aware fallback
- **Desktop_UI**: Electron/React приложение с FastAPI backend для управления агентом
- **Candidate**: Заказ, прошедший этапы фильтрации и находящийся в очереди на обработку
- **Circuit_Breaker**: Механизм защиты от каскадных сбоев при отправке откликов
- **Session_Hub**: Локальный сервер для управления куками авторизации
- **Dry_Run**: Режим работы без реальной отправки откликов на платформу

## Requirements

### Requirement 1: Надёжный парсинг заказов Kwork через API

**User Story:** As a фрилансер, I want чтобы парсинг заказов с Kwork работал стабильно и возвращал актуальные результаты, so that я получаю свежие заказы для обработки каждый цикл.

#### Acceptance Criteria

1. WHEN Kwork_API_Client получает credentials (KWORK_EMAIL и KWORK_PASSWORD), оба из которых являются непустыми строками, THE Kwork_API_Client SHALL авторизоваться и вернуть API-объект, готовый к выполнению запросов, в течение 30 секунд
2. WHEN Kwork_Parser выполняет поисковый запрос, THE Kwork_Parser SHALL вернуть список ProjectItem объектов, в которых поля id и title содержат непустые строки, поле url содержит валидный URL вида https://kwork.ru/projects/{id}, а поля budget, offers_count и client_user_id заполнены значениями из API (или null/0 если источник не предоставил данные)
3. IF авторизация Kwork API завершается HTTP-ошибкой, таймаутом или ответ API не содержит ожидаемого поля `response`, THEN THE Kwork_API_Client SHALL сбросить текущий клиент (установить в None) и выполнить повторную авторизацию при следующем запросе
4. IF Kwork API возвращает пустой ответ или ошибку 3 раза подряд в рамках одного цикла парсинга, THEN THE Kwork_Parser SHALL переключиться на браузерный fallback-парсер и записать в лог уровня WARNING причину переключения, включая текст последней ошибки или факт пустого ответа
5. WHEN браузерный fallback-парсер загружает страницу проектов, THE Kwork_Parser SHALL сначала попытаться извлечь данные из window.stateData JSON-payload, и только если stateData отсутствует или не содержит списка проектов, извлечь данные из HTML-карточек (селектор div.want-card)
6. IF Kwork API возвращает ответ, в котором поле `response` отсутствует, равно null или имеет тип, отличный от ожидаемого (не список/не словарь), THEN THE Kwork_Parser SHALL вернуть пустой список ProjectItem без выброса необработанного исключения
7. WHEN браузерный fallback-парсер загружает страницу проектов, THE Kwork_Parser SHALL дождаться появления контента (селектор div.want-card) не более 10 секунд, и если контент не появился — вернуть пустой список ProjectItem

### Requirement 2: Корректная генерация и маршрутизация поисковых запросов

**User Story:** As a фрилансер, I want чтобы система генерировала релевантные поисковые запросы на основе моего описания и истории, so that я нахожу подходящие заказы, а не мусор.

#### Acceptance Criteria

1. WHEN SEARCH_BRIEF задан (непустая строка) в конфигурации, THE Search_Strategy SHALL сгенерировать через LLM от 1 до QUERY_COUNT (диапазон QUERY_COUNT: 1–20, по умолчанию 6) поисковых запросов длиной от 1 до 3 слов (не более 50 символов каждый) на русском языке, содержащих ключевые слова из описания пользователя или его профиля навыков
2. IF SEARCH_BRIEF не задан или пуст, THEN THE Search_Strategy SHALL использовать значение SEARCH_QUERY (разделённое символом "|") как описание для генерации запросов, а при отсутствии SEARCH_QUERY — использовать значение "python" по умолчанию
3. IF LLM-генерация запросов завершается ошибкой (исключение при вызове или пустой результат парсинга), THEN THE Search_Strategy SHALL использовать fallback-список запросов из SEARCH_QUERY (разделённых "|") или встроенный платформенный список по умолчанию (для kwork: "python", "telegram бот", "парсер", "api", "автоматизация", "скрипт", "flask", "django")
4. WHEN Search_Strategy имеет историю сигналов (shortlisted, sent, skipped), THE Search_Strategy SHALL исключать из результатов запросы с нулевой конверсией (shortlisted_count = 0 И sent_count = 0 И user_preferred = false) за 3 и более запусков, и размещать запросы с положительными сигналами (sent_count > 0 ИЛИ shortlisted_count ≥ 2 ИЛИ user_preferred = true) перед AI-сгенерированными запросами в итоговом списке
5. THE Kwork_Parser SHALL маппить каждый поисковый запрос на category_ids Kwork API путём сопоставления слов запроса с таблицей ключевых слов (например: "python", "парсер", "бот", "автоматизация" → категория 11; "сайт", "django", "react", "верстка" → категория 79)
6. IF поисковый запрос не содержит ни одного ключевого слова из таблицы маппинга, THEN THE Kwork_Parser SHALL использовать категорию 11 (скрипты и автоматизация) как значение по умолчанию

### Requirement 3: Качественная генерация откликов

**User Story:** As a фрилансер, I want чтобы сгенерированные отклики были конкретными, профессиональными и выделялись среди шаблонных ответов, so that заказчики выбирают меня среди конкурентов.

#### Acceptance Criteria

1. WHEN Proposal_Generator получает ProjectItem с описанием и навыками, THE Proposal_Generator SHALL сгенерировать отклик длиной от 3 до 5 предложений, содержащий конкретный технический подход к решению задачи (указание стека, метода или архитектуры, применимых к описанию проекта)
2. IF в портфолио существует хотя бы один кейс с пересечением минимум одной технологии из навыков проекта, THEN THE Proposal_Generator SHALL включить в отклик один кейс с наибольшим количеством совпадающих технологий
3. IF ни один кейс из портфолио не имеет пересечения технологий с навыками проекта, THEN THE Proposal_Generator SHALL сгенерировать отклик без упоминания кейса, сохраняя структуру из 3-5 предложений
4. THE Proposal_Generator SHALL завершить отклик вопросом, который ссылается на конкретную техническую деталь из описания проекта (технологию, интеграцию, ограничение или архитектурное решение)
5. THE Proposal_Generator SHALL очистить сгенерированный текст от: markdown-символов (*, #, _, `), эмодзи, упоминаний цен и денежных сумм, а также вводных фраз вида "Вот ваш отклик", "Конечно", "Безусловно"
6. IF LLM-генерация отклика завершается ошибкой, THEN THE Proposal_Generator SHALL использовать шаблонный генератор как fallback и залогировать ошибку с указанием провайдера и текста исключения
7. THE Proposal_Generator SHALL передавать в LLM контекст о заказчике (рейтинг, количество заказов, процент повторных наймов) для настройки тона отклика, при этом сгенерированный текст не SHALL содержать прямых или косвенных упоминаний профиля заказчика, его статистики, данных из социальных сетей или иных источников за пределами описания проекта

### Requirement 4: Desktop UI для управления агентом

**User Story:** As a фрилансер, I want управлять агентом через Desktop-приложение с наглядным интерфейсом, so that я вижу статус работы, управляю настройками и принимаю решения по откликам без командной строки.

#### Acceptance Criteria

1. THE Desktop_UI SHALL отображать текущий статус Pipeline как одно из значений: idle, running, error — и при статусе running отображать название текущего этапа (parsing, filtering, scoring, vetting, generating, sending) и количество обработанных заказов из общего числа собранных в текущем цикле
2. WHEN пользователь нажимает кнопку запуска цикла, THE Desktop_UI SHALL запустить цикл Orchestrator с параметрами из панели настроек (платформы, SEARCH_BRIEF, лимиты, режим dry-run) и перевести отображаемый статус в running в течение 2 секунд после нажатия
3. IF запуск цикла завершается ошибкой, THEN THE Desktop_UI SHALL отобразить статус error и сообщение с указанием причины сбоя, сохраняя введённые пользователем параметры запуска без сброса
4. THE Desktop_UI SHALL отображать список Candidate с пагинацией (не более 30 элементов на страницу), показывая для каждого: статус, AI-скор (0–10), текст отклика и предоставляя действия approve, skip или редактирование текста и цены
5. THE Desktop_UI SHALL предоставлять страницу настроек для редактирования: SEARCH_BRIEF (до 500 символов), QUERY_COUNT (1–20), PAGES_TO_PARSE (1–10), TOP_PROJECTS (0–50), AI_SCORE_THRESHOLD (1–10) и лимита отправок на платформу (1–20) — с валидацией диапазонов перед отправкой в backend
6. WHEN Desktop_UI передаёт runtime-настройки в backend, THE Desktop_UI SHALL применять их только на время текущего запуска, не перезаписывая секреты и постоянные значения в .env файле, и восстанавливать предыдущие значения переменных окружения после завершения цикла
7. THE Desktop_UI SHALL отображать лог текущего цикла в реальном времени через WebSocket-соединение с backend с задержкой отображения не более 1 секунды от момента записи в лог
8. IF WebSocket-соединение с backend разрывается, THEN THE Desktop_UI SHALL отобразить индикатор потери связи и выполнять автоматические попытки переподключения каждые 5 секунд до восстановления соединения или до 10 попыток

### Requirement 5: Стабильность и наблюдаемость Pipeline

**User Story:** As a фрилансер, I want чтобы система работала стабильно, логировала ошибки и позволяла диагностировать проблемы, so that я могу доверять автоматизации и быстро находить причины сбоев.

#### Acceptance Criteria

1. THE Orchestrator SHALL логировать каждый этап цикла (парсинг, keyword-фильтрация, NLP-фильтрация, AI-скоринг, веттинг, генерация, отправка) с указанием количества элементов на входе и выходе этапа и времени выполнения в миллисекундах
2. IF любой этап Pipeline завершается необработанным исключением при обработке отдельного элемента, THEN THE Orchestrator SHALL залогировать ошибку с указанием этапа и идентификатора элемента, установить статус кандидата в "error" и продолжить обработку оставшихся элементов в текущем цикле
3. WHEN Circuit_Breaker фиксирует 3 последовательных ошибки отправки для одной платформы, THE Circuit_Breaker SHALL перевести состояние платформы в OPEN, приостановить отправку на эту платформу и залогировать длительность паузы в секундах
4. THE Orchestrator SHALL записывать структурированные метрики каждого цикла в SQLite (logs.db): количество спарсенных проектов, прошедших keyword-фильтр, прошедших NLP-фильтр, прошедших AI-скоринг, прошедших веттинг, отправленных и завершившихся ошибкой
5. WHEN цикл завершается, THE Orchestrator SHALL вернуть словарь статистики с ключами parsed, active, filtered, ai_passed, vetted, queued, auto_ready и sent, где каждое значение является целым числом не менее 0
6. IF Kwork API недоступен и браузерный fallback также недоступен, THEN THE Orchestrator SHALL залогировать ошибку уровня ERROR с указанием причины недоступности и завершить цикл штатно, вернув словарь статистики с нулевыми значениями без аварийного завершения процесса
7. WHILE Circuit_Breaker находится в состоянии OPEN для платформы, THE Orchestrator SHALL пропускать отправку откликов на эту платформу и устанавливать статус соответствующих кандидатов в "queued" до восстановления

### Requirement 6: Упрощение архитектуры и удаление мёртвого кода

**User Story:** As a фрилансер, I want чтобы кодовая база содержала только используемый код, so that система проще в поддержке, быстрее запускается и не содержит запутывающих неиспользуемых модулей.

#### Acceptance Criteria

1. IF переменная окружения PLATFORMS содержит только значение "kwork", THEN THE Orchestrator SHALL инициализировать единственный экземпляр парсера KworkAPIParser и не создавать экземпляры FreelanceRuParser или HHParser
2. IF переменная OSINT_ENABLED установлена в "false" или не задана в окружении, THEN THE Orchestrator SHALL не создавать экземпляр OSINTAggregator и не вызывать метод osint.gather в ходе цикла обработки
3. WHEN Pipeline запущен с конфигурацией, содержащей только GROQ_API_KEY, KWORK_EMAIL, KWORK_PASSWORD, SEARCH_BRIEF и PLATFORMS=kwork, THE Pipeline SHALL выполнить полный цикл (парсинг → фильтрация → скоринг → веттинг → генерация отклика) и завершиться без необработанных исключений в течение 120 секунд
4. IF переменная OSINT_PROBIV_PROVIDERS пуста или не задана, THEN THE Orchestrator SHALL не импортировать и не инициализировать модули probiv-провайдеров (emailrep, hibp, leakcheck, intelx, whatsmyname)
5. IF модули платформ freelance_ru или hh_ru отключены (отсутствуют в переменной PLATFORMS), THEN THE Desktop_UI SHALL скрывать секции настроек этих платформ из интерфейса
6. IF переменная OSINT_ENABLED установлена в "false" или не задана, THEN THE Desktop_UI SHALL скрывать секции настроек OSINT и probiv-провайдеров из интерфейса

### Requirement 7: Надёжная авторизация и управление сессиями Kwork

**User Story:** As a фрилансер, I want чтобы авторизация на Kwork работала автоматически и восстанавливалась при протухании сессии, so that парсинг и отправка откликов не прерываются из-за проблем с авторизацией.

#### Acceptance Criteria

1. WHEN Session_Hub доступен по SESSION_HUB_URL, THE Kwork_API_Client SHALL получать куки из Session_Hub как приоритетный источник авторизации, используя HTTP GET-запрос с таймаутом не более 10 секунд
2. IF Session_Hub недоступен и SESSION_HUB_REQUIRED установлен в true, THEN THE Kwork_API_Client SHALL отказать в инициализации и залогировать ошибку с указанием причины без попытки прямой авторизации
3. IF Session_Hub недоступен и SESSION_HUB_REQUIRED установлен в false, THEN THE Kwork_API_Client SHALL использовать KWORK_EMAIL и KWORK_PASSWORD для прямой авторизации через мобильный API
4. IF Session_Hub недоступен, SESSION_HUB_REQUIRED установлен в false, и переменные KWORK_EMAIL или KWORK_PASSWORD не заданы, THEN THE Kwork_API_Client SHALL залогировать предупреждение и вернуть отсутствие API-клиента без выброса исключения
5. IF авторизация через API возвращает ошибку аутентификации (HTTP 401 или явный признак невалидных credentials в ответе), THEN THE Kwork_API_Client SHALL выполнить одну повторную попытку авторизации с задержкой 5 секунд и залогировать результат
6. IF повторная попытка авторизации также завершается ошибкой, THEN THE Kwork_API_Client SHALL залогировать финальную ошибку и вернуть отсутствие API-клиента, не выбрасывая исключение вызывающему коду
7. WHEN Kwork_API_Client получает ответ API, содержащий признак невалидной сессии (ключ "response" отсутствует или содержит ошибку авторизации), THE Kwork_API_Client SHALL сбросить текущий API-клиент и создать новый при следующем обращении к get_api, но не более 3 сбросов подряд в рамках одного цикла парсинга

### Requirement 8: Фильтрация и скоринг заказов

**User Story:** As a фрилансер, I want чтобы система отсеивала нерелевантные заказы и ранжировала подходящие по качеству, so that я трачу время только на перспективные проекты.

#### Acceptance Criteria

1. THE Pipeline SHALL отфильтровывать заказы, в заголовке или описании которых встречается хотя бы одно стоп-слово из config/filters.yaml (регистронезависимое подстрочное совпадение), до этапа AI-скоринга
2. IF у заказа указан бюджет и он ниже min_budget или выше max_budget из config/filters.yaml, THEN THE Pipeline SHALL отфильтровать этот заказ до этапа AI-скоринга
3. WHEN AI-скоринг оценивает заказ, THE Pipeline SHALL присвоить целочисленный скор от 1 до 10 и пропустить дальше только заказы со скором не ниже значения переменной AI_SCORE_THRESHOLD (по умолчанию 6)
4. THE Pipeline SHALL дедуплицировать заказы по комбинации (platform, project_id) в рамках одного цикла, сохраняя только первое вхождение
5. IF заказ уже имеет статус из группы BLOCKING_STATUSES (queued, snoozed, manual_sent, auto_sent, draft, skipped) в базе данных, THEN THE Pipeline SHALL пропустить его без повторной обработки
6. IF у заказа отсутствует значение бюджета (null или не указано), THEN THE Pipeline SHALL пропустить бюджетный фильтр для этого заказа и передать его на следующий этап

### Requirement 9: Отправка откликов с подтверждением

**User Story:** As a фрилансер, I want подтверждать или редактировать отклики перед отправкой, so that на платформу уходят только качественные и проверенные мной тексты.

#### Acceptance Criteria

1. WHEN Candidate достигает статуса auto_ready в режиме semi_auto, THE Orchestrator SHALL отправить уведомление в Desktop_UI с текстом отклика и предложенной ценой для подтверждения; IF Desktop_UI недоступен, THEN THE Orchestrator SHALL отправить уведомление в Telegram; IF оба канала недоступны, THEN THE Orchestrator SHALL сохранить Candidate в статусе pending_review и повторить попытку уведомления при следующем цикле
2. WHEN пользователь подтверждает отклик (approve), THE Orchestrator SHALL отправить отклик на платформу Kwork через браузерный flow в течение 60 секунд и обновить статус на manual_sent; IF браузерный flow не завершается за 60 секунд, THEN THE Orchestrator SHALL считать отправку неуспешной
3. WHEN пользователь редактирует текст или цену перед подтверждением, THE Orchestrator SHALL валидировать отредактированные значения (текст от 1 до 2000 символов, цена в пределах min_budget и max_budget из config/filters.yaml) и использовать их при отправке
4. IF отредактированный текст или цена не проходят валидацию, THEN THE Orchestrator SHALL отклонить отправку, отобразить сообщение об ошибке с указанием нарушенного ограничения и сохранить Candidate в статусе pending_review для повторного редактирования
5. IF отправка отклика на платформу завершается ошибкой, THEN THE Orchestrator SHALL обновить статус Candidate на error, записать причину ошибки и уведомить пользователя через тот же канал, по которому было отправлено исходное уведомление
6. WHILE режим работы установлен в dry_run, THE Orchestrator SHALL сохранять все сгенерированные отклики как draft без реальной отправки на платформу

### Requirement 10: Расширяемость LLM-провайдеров

**User Story:** As a фрилансер, I want чтобы архитектура позволяла подключать дополнительных LLM-провайдеров в будущем, so that я могу переключиться на более качественную или дешёвую модель без переписывания кода.

#### Acceptance Criteria

1. THE LLM_Router SHALL поддерживать task-specific маршрутизацию, позволяя назначить отдельного провайдера и модель для каждой из задач: query_generation, scoring и proposal_writing через переменные окружения вида {TASK}_PROVIDER и {PROVIDER}_MODEL_{TASK}
2. WHEN провайдер возвращает ошибку (HTTP-статус 5xx, таймаут соединения свыше 60 секунд или пустой ответ), THE LLM_Router SHALL автоматически переключиться на следующий доступный провайдер из списка, отсортированного по убыванию health-score, перебирая не более количества зарегистрированных провайдеров
3. IF все зарегистрированные провайдеры вернули ошибку для данного запроса, THEN THE LLM_Router SHALL выбросить исключение с указанием задачи (task) и ошибки последнего провайдера
4. THE LLM_Router SHALL вести in-memory статистику каждого провайдера (количество успехов, количество ошибок, число последовательных ошибок, время последнего успеха, время последней ошибки, текст последней ошибки) и предоставлять метод get_provider_health, возвращающий эти данные вместе с вычисленным health-score для каждого провайдера
5. WHEN новый LLM-провайдер добавляется в конфигурацию (API-ключ в .env), THE LLM_Router SHALL подключить его при инициализации и сделать доступным для маршрутизации и fallback без изменения кода модулей, вызывающих метод generate
