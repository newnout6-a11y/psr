Исследование методов обхода блокировок Memory-Mapped I/O в ОС Windows: Низкоуровневый доступ к базам данных SQLite (Google Chrome) в пользовательском режиме
Введение и фундаментальная проблематика
В современных операционных системах семейства Windows механизмы управления конкурентным доступом к файлам (File Locking) представляют собой сложную многоуровневую архитектуру, интегрирующую диспетчер ввода-вывода (I/O Manager), диспетчер памяти (Memory Manager) и диспетчер объектов (Object Manager). Одной из наиболее нетривиальных задач в области системного программирования, цифровой криминалистики и тестирования на проникновение является получение безопасного доступа к файлам, которые эксклюзивно заблокированы активными процессами. Классическим и наиболее показательным примером такой проблематики является попытка извлечения базы данных Cookies (формат SQLite), принадлежащей активному процессу браузера Google Chrome, в условиях строгого пользовательского режима, то есть в отсутствие привилегий администратора и без возможности обхода системы контроля учетных записей (UAC).
Анализ исходных данных инцидента и системных журналов выявляет критическую аномалию: в процессе извлечения фиксируется потеря данных (логи показывают успешное чтение 3694 записей куки вместо ожидаемых 4567). При этом попытки применения штатных утилит резервного копирования, в частности esentutl.exe /y, завершаются скрытым сбоем. В журналах выполнения шаг с использованием esentutl полностью отсутствует, а стандартный поток вывода (stdout) утилиты бесследно "проглатывается" операционной системой. Стандартные подходы с использованием Win32 API, такие как вызовы CopyFileW или CreateFileW с флагами максимального разделения доступа (GENERIC_READ совместно с FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE), неизменно возвращают системную ошибку ERROR_SHARING_VIOLATION (код 32).1
Ключевая техническая деталь, определяющая несостоятельность классических методов обхода (таких как дублирование дескрипторов), заключается в феномене fileid_match=0. При энумерации дескрипторов целевого процесса скрипт не обнаруживает совпадений по идентификатору файла или его имени. Это свидетельствует о том, что процесс Chrome не удерживает стандартный файловый дескриптор. Файл заблокирован на уровне файловой системы через механизмы отображения файлов в память (Memory-Mapped I/O), реализуемые связкой системных вызовов CreateFileMapping и MapViewOfFile.4
В данном исследовании представлен исчерпывающий архитектурный и программный анализ причин несостоятельности стандартных утилит командной строки. Особое внимание уделяется разбору парадокса отсутствующего дескриптора (fileid_match=0) и разработке методологии низкоуровневого доступа к данным через Native API (C/WinAPI). Дополнительно рассматривается проблематика синхронизации SQLite в режиме Write-Ahead Logging (WAL) и анализируются новейшие механизмы защиты App-Bound Encryption (ABE), внедренные в экосистему Chromium начиная с версии 127, которые делают простое физическое копирование базы данных недостаточным для извлечения секретов.1
Архитектура диспетчера ввода-вывода и природа блокировки Memory-Mapped I/O
Для понимания природы эксклюзивной блокировки файла Cookies необходимо детально рассмотреть внутреннюю архитектуру работы ОС Windows с разделяемыми ресурсами и объектами памяти.
Взаимодействие диспетчера ввода-вывода и ShareMode
При каждом обращении к файловой системе через высокоуровневую функцию CreateFile или ее низкоуровневый системный аналог NtCreateFile, диспетчер ввода-вывода (I/O Manager) оценивает запрошенные права доступа (DesiredAccess) и режим совместного использования (ShareAccess). Если первичный процесс открывает файл, определяя параметр ShareAccess таким образом, что он не включает флаг FILE_SHARE_READ (или включает его совместно с другими эксклюзивными требованиями), диспетчер ввода-вывода фиксирует этот факт в блоке управления файлом FCB (File Control Block).2 Любая последующая попытка вторичного процесса открыть этот файл, даже с минимальными правами для простого чтения, приведет к тому, что функция NtCreateFile вернет статус STATUS_SHARING_VIOLATION (0xC0000043), который в парадигме Win32 API транслируется как ошибка 32 (ERROR_SHARING_VIOLATION).3
Браузеры на базе архитектуры Chromium интенсивно используют механизмы транзакционной записи и кэширования пользовательского профиля. При инициализации базы данных SQLite, ядро СУБД запрашивает жесткие блокировки. Однако ключевая специфика движка Chrome заключается в создании объектов отображения файлов в виртуальную память.
Механика CreateFileMapping и интеграция с диспетчером памяти
Когда браузер вызывает CreateFileMapping на базе открытого файлового дескриптора, диспетчер объектов (Object Manager) создает новый объект ядра — объект секции (Section Object). В этот момент в игру вступает диспетчер памяти (Memory Manager). Процесс проецирования секции в виртуальное адресное пространство процесса осуществляется посредством вызова MapViewOfFile.4
Использование Memory-Mapped I/O (MMIO) кардинально меняет семантику доступа и блокировок файловой системы. В момент, когда файл проецируется в память, диспетчер памяти жестко блокирует любые возможности изменения размера файла (усечения) сторонними процессами для предотвращения аппаратных исключений PAGE_FAULT, которые могли бы возникнуть при обращении к несуществующим страницам.10 Более того, классические блокировки диапазонов байтов (Byte Range Locks), которые традиционно используются ядром SQLite для управления параллельным доступом к файлу, полностью игнорируются операционной системой при активном использовании файлов, отображаемых в память.11
Это означает, что стандартная логика попыток открыть файл через CreateFileW с флагами GENERIC_READ и FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE обречена на провал. Ядро Windows защищает целостность страниц памяти, спроецированных в кэш процессов Chrome, и отказывает в конфликтующем доступе на уровне диспетчера кэша (Cache Manager) и диспетчера памяти.

Проблема утилиты ESENTUTL.EXE и пропавший стандартный вывод
Утилита командной строки esentutl.exe, входящая в состав подсистемы Extensible Storage Engine (ESE) ОС Windows, предоставляет мощные механизмы для обслуживания системных баз данных.12 В контексте извлечения заблокированных артефактов широко применяется параметр /y, который изначально предназначен для прямого копирования файлов в обход стандартных блокировок совместного доступа.13
Детальный реверс-инжиниринг и анализ поведения esentutl /y показывает, что успешное копирование эксклюзивно заблокированных файлов достигается за счет неявного обращения утилиты к службе теневого копирования томов (Volume Shadow Copy Service, VSS) через вызовы соответствующих COM-интерфейсов.13 Служба VSS создает мгновенный снимок (Snapshot) тома на уровне драйвера файловой системы (volsnap.sys), что позволяет читать данные напрямую из снимка, игнорируя пользовательские блокировки ввода-вывода.
Фундаментальная проблема данного подхода кроется в модели безопасности ОС Windows. Архитектура VSS требует от вызывающего процесса обязательного наличия в его маркере доступа (Access Token) привилегии SeBackupPrivilege.16 Если утилита esentutl запускается от имени стандартного пользователя без процесса повышения привилегий через UAC, эта привилегия в токене отключена или полностью отсутствует. При попытке инициализации VSS-провайдера вызов COM-интерфейса возвращает ошибку E_ACCESSDENIED.
Феномен исчезновения (проглатывания) стандартного потока вывода (stdout) при запуске esentutl 18, на который указывает исходный запрос, имеет глубокие технические корни в механизмах управления консолью Windows. Когда esentutl.exe сталкивается с критической ошибкой инициализации VSS из-за нехватки привилегий, алгоритм утилиты осуществляет попытку резервного копирования стандартными методами, которые мгновенно завершаются ошибкой ERROR_SHARING_VIOLATION. На этом этапе механизм обработки исключений утилиты, вместо вывода структурированного сообщения об ошибке в перенаправленный анонимный канал (Pipe), может выполнять вызовы низкоуровневых API для прямого вывода в консольный буфер (минуя STD_OUTPUT_HANDLE) или аварийно завершать работу (ExitProcess), не сбрасывая (flush) буферы вывода.18 В результате вызывающий скрипт получает пустой поток вывода и код возврата, свидетельствующий о сбое, при этом в логах не остается следов выполнения фазы резервного копирования.
Ограничения NtCreateFile и флагов резервного копирования
Альтернативным направлением разработки является прямое использование недокументированных флагов Native API, в частности вызова NtCreateFile с параметром FILE_OPEN_FOR_BACKUP_INTENT (0x00004000).16 Данный флаг является инструкцией для диспетчера ввода-вывода проигнорировать стандартные проверки списков контроля доступа (ACL) и попытаться предоставить доступ для чтения или записи в обход конфликтов совместного использования.19
Однако, как и в случае с esentutl, драйвер файловой системы (например, NTFS) на этапе обработки IRP (I/O Request Packet) проверяет наличие у вызывающего потока активных привилегий SeBackupPrivilege или SeRestorePrivilege.16 Поскольку исходные условия задачи строго исключают наличие прав администратора, вызов NtCreateFile с данным флагом прерывается менеджером безопасности (Security Reference Monitor, SRM) с возвратом статуса STATUS_PRIVILEGE_NOT_HELD (0xC0000061).
Аналогичная судьба постигает и попытки использовать сторонние утилиты на базе VSS, такие как HoboCopy 23, так как они упираются в тот же непреодолимый барьер привилегий пользовательского режима.
Парадокс отсутствующего дескриптора: Разрешение проблемы fileid_match=0
Одной из самых технически сложных проблем, описанных в исходном запросе, является аномалия дублирования дескрипторов (Handle Duplication). Стандартная техника обхода заключается в поиске процесса, удерживающего блокировку (в данном случае chrome.exe), и клонировании его файлового дескриптора в адресное пространство атакующего приложения. Однако диагностические логи показывают fileid_match=0, что означает, что при переборе всех дескрипторов процесса Chrome скрипт не находит ни одного объекта типа File, имя которого соответствовало бы целевой базе данных Cookies.
Существует устойчивое заблуждение, что любой заблокированный файл обязательно имеет соответствующий файловый дескриптор в таблице процесса-владельца. Феномен fileid_match=0 объясняется глубокой спецификой реализации Memory-Mapped I/O в операционных системах Windows.4
Жизненный цикл File Object и Section Object
Когда браузер Chrome инициирует работу с базой данных Cookies, он выполняет следующую последовательность системных вызовов:
1. Вызывается CreateFileW (или NtCreateFile), что создает объект типа File (File Object) в ядре и возвращает его дескриптор в таблицу дескрипторов процесса Chrome.
2. Вызывается CreateFileMappingW (или NtCreateSection), используя полученный файловый дескриптор в качестве базы. Это создает объект ядра типа Section (Section Object).
3. Вызывается MapViewOfFile (или NtMapViewOfSection), который проецирует секцию в виртуальное адресное пространство процесса.
4. Критический шаг: Для оптимизации использования ресурсов и предотвращения утечек, логика Chrome (вслед за рекомендациями MSDN 4) вызывает CloseHandle для первоначального файлового дескриптора и, зачастую, для дескриптора секции.
Официальная документация Microsoft прямо заявляет: "Mapped views of a file mapping object maintain internal references to the object... you cannot close the underlying file-mapping object and still use the views" (Отображаемые представления объекта сопоставления файлов поддерживают внутренние ссылки на объект... вы можете закрыть дескриптор файла после создания объекта сопоставления, и это не повлияет на отображение).4
Поскольку диспетчер памяти (Mm) удерживает внутреннюю ссылку на объект файла до тех пор, пока память не будет явно освобождена через UnmapViewOfFile, операционная система продолжает считать файл эксклюзивно заблокированным. Однако в таблице дескрипторов процесса chrome.exe дескриптор с типом File (обычно имеющий ObjectTypeNumber равный 0x1E или 0x24 в зависимости от версии Windows) для файла Cookies больше не существует. Именно поэтому эвристический поиск по идентификатору файла или пути возвращает fileid_match=0. Процесс Chrome не держит обычный хэндл; блокировка поддерживается архитектурой управления виртуальной памятью на уровне ядра.

Метод 1: Дублирование дескриптора секции (Section Handle Duplication)
Если процесс Chrome не закрыл дескриптор секции (Section Object), сценарий обхода fileid_match=0 требует изменения алгоритма поиска. В операционной системе Windows каждый тип объекта ядра имеет свой ObjectTypeNumber. Инструментарий должен извлекать снимок системы с помощью NtQuerySystemInformation (информационный класс SystemHandleInformation — 0x10) 24, но искать не объекты типа File, а объекты типа Section (значения зависят от версии ОС, например, 0x25 или 0x2A).
Если дескриптор секции обнаружен, алгоритм использует NtDuplicateObject для его копирования из адресного пространства Chrome в адресное пространство атакующего процесса.27 Поскольку секция уже содержит права доступа к ассоциированному файлу, атакующий процесс может напрямую вызвать MapViewOfFile (или NtMapViewOfSection), используя дублированный дескриптор секции. Это позволяет ОС спроецировать данные базы Cookies напрямую в оперативную память атакующего процесса, полностью минуя необходимость вызова CreateFileW и игнорируя проверку ShareMode на уровне диспетчера ввода-вывода. После этого данные просто копируются из памяти в новый локальный файл на диске.
Метод 2: Прямое чтение виртуальной памяти процесса (In-Memory Extraction)
В сценариях, где Chrome агрессивно закрывает как дескрипторы файла, так и дескрипторы секций (оставляя только активные страницы в дереве VAD — Virtual Address Descriptor), даже продвинутое дублирование дескрипторов потерпит фиаско. В этом случае единственным 100% рабочим вектором является полный отказ от взаимодействия с файловой системой и переход к чтению оперативной памяти.
Поскольку функция MapViewOfFile проецирует содержимое SQLite-базы непосредственно в виртуальное адресное пространство процесса chrome.exe, вся необходимая информация физически находится в RAM. Так как атакующий скрипт запущен от имени того же пользователя, что и Chrome, он имеет законное право получить дескриптор процесса с правами PROCESS_VM_READ | PROCESS_QUERY_INFORMATION (без необходимости обхода UAC).
Техника, получившая распространение в инструментах класса CookieKatz 1, заключается в следующем:
1. Вызов OpenProcess для chrome.exe.
2. Сканирование виртуальной памяти процесса (Virtual Memory Enumeration) с помощью VirtualQueryEx в поисках регионов памяти со статусом MEM_MAPPED или MEM_IMAGE.
3. Идентификация региона, содержащего магические байты заголовка SQLite (SQLite format 3\0).
4. Извлечение всей базы данных напрямую из оперативной памяти целевого процесса с использованием ReadProcessMemory (или прямого системного вызова NtReadVirtualMemory).
Данный метод не просто решает проблему заблокированного файла, он делает саму концепцию файловых блокировок нерелевантной, так как взаимодействие с дисковой подсистемой не происходит вовсе.
Анализ альтернативных I/O флагов (FILE_SUPERSEDED и FILE_OPEN_FOR_FREE_SPACE_QUERY)
В исследовательских запросах часто фигурируют попытки обойти блокировки через экзотические флаги NtCreateFile.
* Использование диспозиции FILE_SUPERSEDED (0x00000000) 29 подразумевает удаление существующего файла и создание нового на его месте. Однако эта операция требует от вызывающего потока наличия прав DELETE для целевого файла, а диспетчер ввода-вывода все равно проверяет, разрешает ли текущая блокировка Chrome удаление файла (FILE_SHARE_DELETE). В подавляющем большинстве случаев MMIO-блокировки не допускают усечения или удаления, что делает FILE_SUPERSEDED неэффективным.32
* Флаг FILE_OPEN_FOR_FREE_SPACE_QUERY (0x00800000) в функции NtOpenFile 2 применяется фильтрами файловых систем для оценки свободного пространства без запроса оппортунистических блокировок (oplocks). Несмотря на то, что он может позволить открыть дескриптор заблокированного файла, такой дескриптор лишен прав FILE_READ_DATA, что делает невозможным чтение пользовательских данных (возникает ошибка STATUS_ACCESS_DENIED при вызове NtReadFile).
Таким образом, чтение виртуальной памяти или дублирование дескрипторов секций остаются единственными жизнеспособными парадигмами.
Преодоление внутренних механизмов SQLite в режиме WAL
Предположим, что база данных Cookies успешно извлечена (скопирована на диск) одним из вышеописанных методов (Memory Dumping или Section Mapping). Однако попытка прочитать данные может выявить расхождение: логи показывают 3694 куки, тогда как ожидалось 4567. Эта проблема имеет архитектурную природу, связанную с самой СУБД SQLite.
Специфика Write-Ahead Logging (WAL)
Современные версии браузеров на базе Chromium перевели большинство своих локальных баз данных SQLite в режим WAL (Write-Ahead Logging).34 В этом режиме ядро СУБД не вносит изменения напрямую в основной файл базы данных. Вместо этого все новые транзакции последовательно дописываются в отдельный файл журнала (например, Cookies-wal). Перенос данных из WAL-файла в основной файл базы данных (операция Checkpoint) происходит асинхронно.
Когда алгоритм обхода блокировок делает мгновенный снимок (Snapshot) основного файла Cookies из памяти или с диска, он копирует базу данных в "грязном" (inconsistent) состоянии. Часть свежих данных (недостающие 873 записи) физически находится в файле Cookies-wal, а в самом файле Cookies они еще не зафиксированы. Более того, при попытке открыть скопированную, но незавершенную базу данных через стандартный коннектор SQLite, драйвер попытается инициировать процедуру восстановления и может выдать внутреннюю ошибку database is locked (теперь уже на уровне блокировок самого SQLite VFS) или SQLITE_CORRUPT.36
Обход блокировок VFS с помощью параметра immutable=1
Для обеспечения стабильного чтения данных из таких сырых слепков применяется специализированный метод инициализации подключения к SQLite через URI с параметром immutable=1.36
Формат строки подключения в программном коде выглядит следующим образом:
file:C:/Temp/Copy_Cookies.sqlite?immutable=1
Наличие параметра immutable в URI-строке инструктирует внутреннюю виртуальную файловую систему (VFS) SQLite о том, что файл физически располагается на носителе "только для чтения".36 При этом ядро SQLite радикально меняет свое поведение:
1. Отключение блокировок ОС: Движок полностью отключает вызовы системных функций блокировки файлов (xLock и xUnlock), не пытаясь установить разделяемые или эксклюзивные блокировки на скопированный файл.36
2. Игнорирование WAL-журнала: SQLite перестает искать ассоциированные WAL-файлы и не пытается выполнить откат (Rollback) или накат (Checkpoint) транзакций.
3. Чтение "как есть": Разрешается выполнение SQL-запросов (например, SELECT name, encrypted_value FROM cookies) непосредственно к основному файлу в том виде, в котором он был зафиксирован в момент копирования.
Это элегантное решение позволяет игнорировать внутренние конфликты транзакций SQLite и гарантированно извлекать те данные, которые уже были перенесены в основной файл (в нашем случае — 3694 записи). Для получения полного набора данных (4567 записей) алгоритму извлечения потребовалось бы дополнительно скопировать и проанализировать файл Cookies-wal перед выполнением запроса, что часто затруднено теми же механизмами MMIO.
Пост-эксплуатация: Преодоление App-Bound Encryption (ABE) в Chromium
Получение физического доступа к файлу Cookies является лишь первой фазой извлечения данных. Начиная с июля 2024 года (релиз Google Chrome версии 127), ландшафт локальной безопасности претерпел тектонические изменения благодаря внедрению корпорацией Google механизма Application-Bound Encryption (ABE).1
Исторически, до версии 127, секреты в Chrome защищались связкой мастер-ключа из файла Local State и Windows Data Protection API (DPAPI).38 Вредоносному ПО (инфостилерам) или исследователю было достаточно прочитать файл Local State, вызвать CryptUnprotectData в контексте текущего пользователя и расшифровать AES-ключ, которым затем расшифровывалось поле encrypted_value из SQLite.39
Архитектура App-Bound Encryption (ABE) фундаментально усложнила этот процесс. Теперь зашифрованные данные привязаны не только к профилю пользователя ОС, но и к криптографической идентичности самого приложения (chrome.exe). Во время инициализации служба повышения привилегий Chrome (IElevator service), функционирующая с системными правами (NT AUTHORITY\SYSTEM), кодирует идентичность вызывающего процесса в структуру данных. При попытке дешифровки эта же служба проверяет цифровую подпись процесса, валидирует путь исполнения (Process Path Authentication) и анализирует стек вызовов.1 Если дешифровку запрашивает любой сторонний процесс, отличный от легитимного браузера (даже работающий от имени того же пользователя), запрос блокируется, и в журнале Application Log ОС Windows фиксируется событие Event ID 257 («Failed to authenticate caller process»).1
Продвинутые векторы обхода механизма ABE
Анализ современного инструментария показывает, что защита ABE не является абсолютной и может быть преодолена в непривилегированном режиме с использованием изощренных методов системного программирования.1
1. Взаимодействие через COM-интерфейс IElevator (Process Hollowing)
Служба проверки подлинности ABE работает через механизмы Component Object Model (COM). Чтобы обойти проверку пути и подписи, исследователи безопасности (в частности, в проекте Chrome-App-Bound-Encryption-Decryption от автора xaitax 41) применяют технологии внедрения кода (Reflective Process Hollowing / Direct Syscall Injection). Атакующий скрипт создает новый легитимный процесс браузера в приостановленном состоянии (CREATE_SUSPENDED), внутри которого размещается полезная нагрузка. После возобновления потока, полезная нагрузка инициирует легитимное COM-соединение с сервисом Chrome Elevation Service, используя Class Identifier (CLSID) Chrome. Поскольку запрос исходит изнутри валидного процесса chrome.exe, служба ABE успешно аутентифицирует вызывающую сторону и возвращает дешифрованный 32-байтный AES-256 ключ. Этот ключ применяется к секретам, имеющим новый префикс v20 (вместо старого v10 от DPAPI).1
2. Вектор Chromium Remote Debugging
Альтернативный метод обхода, который активно эксплуатируется современными инфостилерами (Phemedrone, Stealc, LummaC2), основан на использовании легитимного порта удаленной отладки Chrome DevTools Protocol (CDP).1 Программа запускает новый экземпляр браузера с параметрами командной строки: --remote-debugging-port=9222 --headless --window-position=-2400,-2400 --user-data-dir=... В данном сценарии расшифровку куки-файлов осуществляет сам легитимный браузер в фоновом режиме. Сторонняя программа лишь подключается к порту 9222 через WebSocket-интерфейс и отправляет JSON-команду (Network.getAllCookies) на выгрузку уже расшифрованных сессионных куки в виде открытого текста. Этот подход элегантно обходит криптографическую защиту ABE, делегируя расшифровку самому Chrome, однако оставляет заметные артефакты в виде подозрительных аргументов командной строки, которые легко детектируются системами мониторинга (EDR).1

Практическая реализация описанного алгоритма на языках C/C++ с использованием WinAPI и Native API сопряжена с риском обнаружения системами класса EDR (Endpoint Detection and Response) и современными антивирусными комплексами. Защитные решения устанавливают перехватчики (User-land Hooks) внутри системной библиотеки ntdll.dll, анализируя вызовы функций, таких как NtOpenProcess, NtDuplicateObject или NtReadVirtualMemory.
Для обеспечения скрытного выполнения (OPSEC) разработка ведется с применением парадигмы прямых системных вызовов (Direct Syscalls).41
1. Динамическое разрешение системных вызовов: В бинарный код не включаются явные импорты из ntdll.dll. Вместо этого используются техники класса Hell's Gate или Halo's Gate, которые парсят структуру PEB (Process Environment Block) в памяти, находят загруженный образ ntdll.dll и извлекают номера системных вызовов (SSN — System Service Numbers) напрямую из инструкций процессора.
2. Уклонение от статического анализа: Строковые имена функций (например, NtQuerySystemInformation) полностью удаляются из исходного кода. Поиск функций осуществляется путем сравнения хешей (используются алгоритмы DJB2, FNV-1a или MurmurHash3), что исключает наличие подозрительных строк, которые могли бы спровоцировать срабатывание эвристических анализаторов.41
3. Исполнение инструкций syscall: Вызовы к ядру операционной системы выполняются через ассемблерные вставки (инструкция syscall), расположенные непосредственно в памяти полезной нагрузки, что позволяет полностью миновать пользовательские хуки (API Hooks) в ntdll.dll, делая процесс чтения виртуальной памяти Chrome или дублирования дескрипторов секций невидимым для большинства средств мониторинга активности процессов.42
Синтез и стратегические выводы
Проведенное исследование исчерпывающе отвечает на технические вызовы, связанные с конкурентным доступом к базам данных SQLite в среде Windows, и объясняет наблюдаемые в логах аномалии.
Анализ архитектуры диспетчера ввода-вывода и диспетчера памяти ОС Windows подтверждает, что при использовании механизмов Memory-Mapped I/O (связка CreateFileMapping и MapViewOfFile) стандартные методы копирования файлов обречены на неудачу с кодом ERROR_SHARING_VIOLATION. Система защищает целостность страниц памяти, блокируя параллельный доступ.
Пропажа стандартного вывода (swallowed stdout) утилиты esentutl.exe /y и отсутствие следов резервного копирования в журналах является прямым следствием попытки эксплуатации службы теневого копирования томов (VSS) в условиях непривилегированного режима. Нехватка привилегии SeBackupPrivilege вызывает сбой COM-инициализации провайдера VSS, что приводит к некорректному прерыванию работы утилиты в обход перенаправленных пайпов вывода.
Разрешение парадокса fileid_match=0 лежит в плоскости понимания жизненного цикла объектов ядра. Приложение Chrome закрывает файловый дескриптор сразу после создания объекта секции и отображения его в память. Следовательно, в таблице дескрипторов процесса отсутствуют объекты типа File, что делает традиционный метод Handle Duplication неработоспособным.
Для преодоления данного ограничения в рамках C/WinAPI-разработки рекомендуется применять один из двух низкоуровневых векторов:
1. Дублирование дескриптора типа Section (а не File) с последующим его проецированием в память атакующего процесса через MapViewOfFile.
2. Прямое чтение виртуальной памяти целевого процесса (Virtual Memory Dumping) с использованием NtReadVirtualMemory для поиска и извлечения структур SQLite непосредственно из оперативной памяти chrome.exe, полностью игнорируя файловые блокировки.
Работа со скопированными SQLite-артефактами в режиме WAL требует использования строки подключения file:.../Cookies?immutable=1, что позволяет отключить внутренние транзакционные блокировки ядра SQLite (отмена вызовов xLock) и выполнить извлечение данных (тех самых 3694 куки) даже из незавершенного слепка файла. Наконец, для извлечения ценности из скопированных баз в версиях Chrome 127 и выше, необходимо внедрение техник обхода App-Bound Encryption (ABE), таких как использование портов удаленной отладки (CDP) или инъекция в легитимный процесс для взаимодействия с COM-сервисом IElevator. В совокупности с использованием прямых системных вызовов (Direct Syscalls), данные методы формируют надежную и скрытную архитектуру извлечения данных в обход любых файловых блокировок ОС Windows.
